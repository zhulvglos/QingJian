## 方案与免费边界

选择 **Supabase Free：Auth 邮箱 OTP + Postgres + RLS + 比较版本 RPC**。不增加客户端依赖，复用 Rust reqwest、rusqlite 和 Windows keyring。身份校验交给成熟服务，不在轻笺生成或校验验证码。

| 方案 | 核查结果 | 本次选择 |
| --- | --- | --- |
| Supabase Auth + Postgres | 邮箱 OTP、原生行权限、数据库事务能构成一个闭环 | 采用 |
| Firebase Spark | 免费邮箱链接登录每天 5 封，主要是链接流程，不直接满足数字验证码；Firestore 需要另一套适配 | 不采用 |
| 自建认证 + 数据库 | 自行承担验证码安全、风控、会话和维护 | 不采用 |
| Supabase 默认发信 | 只向项目团队邮箱发送；2 封/小时，非生产发信服务，无送达保证；免费默认发信的模板自定义存在限制 | 仅作为项目团队邮箱的连接验证，不能据此承诺普通邮箱 OTP 可用 |
| Supabase + Resend Free SMTP | 3,000 封/月、100 封/日；测试域仅发往自身注册邮箱，向其他邮箱需要验证自有域名 | 无现有域名时不选择，不购买域名 |
| Supabase + Brevo Free SMTP | 300 封/日；发件人验证、域名认证及账户审核受限制，官方不推荐免费个人邮箱作为发件人 | 不把“免费额度”视为无需域名、可任意投递的保证 |
| Supabase + 已有邮箱 SMTP | 可由项目管理员配置一个独立发件邮箱的 SMTP 服务；发信授权码只在云端保存 | **个人最小试用优先路径**；以实际账户是否允许第三方云端 SMTP、发送限额及 QQ 实收为开通条件，未验证前不承诺可用 |

当前 Supabase Free 条件：每项目 500 MB 数据库、每月 50,000 活跃用户、5 GB 出站流量、最多 2 个活跃免费项目；闲置一周可能暂停；不含自动数据库备份和 SLA。暂停后到控制台恢复，客户端继续本地保存并重试。不启用 Pro、支付方式、收费附加项或自动扣费。额度或条款以后可能变化；每次开通以控制台为准。

500 MB 包含便签、笔记、删除墓碑、幂等回执及索引，不是全部用于正文。回执仅存请求 SHA-256 摘要与版本，不积累历史正文。第一版不清理墓碑与回执，以防旧设备复活删除内容；使用时间长后需评估容量，不能承诺无限永久免费。

## 最少开通步骤（需用户另行确认）

1. 确认允许创建一个 Supabase **Free** 项目。选择使用地区并确认本人网络可达、免费计划无需支付方式；出现付费或绑卡要求立即停止。
2. 在项目 SQL Editor 中运行 `cloud/001_sync.sql`；这是一次性迁移，不重复执行。随后只在隔离验收项目运行 `cloud/002_acceptance.sql` 验证权限、幂等、CAS 和墓碑，脚本末尾回滚合成账号和内容。脚本未在真实 Postgres 执行过，本次不能声称 RLS 已部署验收。
3. 管理员在 Authentication 配置 Email 登录、自定义 SMTP 和验证码邮件模板。模板必须包含 `{{ .Token }}`（例如“轻笺验证码：{{ .Token }}，5 分钟内有效”），不要只保留确认链接。开启邮箱确认，禁止匿名登录，不启用 QQ OAuth。SMTP 用户名、授权码、供应商密钥只填在云端控制台；不要发到聊天、源码或报告中。
4. 在服务端设置：OTP 长度 6 位、有效期 **300 秒**；同邮箱重发最小间隔 **60 秒**（`smtp_max_frequency`）；项目发信上限建议 **10 封/小时**（`rate_limit_email_sent`，不超过发信商上限）；验证请求建议 **5 次/5 分钟/IP**（`rate_limit_verify`）。最终可配置粒度以控制台/API为准。Supabase 的验证限流按 IP 的请求窗口计数，**不是每个验证码连续失败 5 次就锁定**。如果需要后者，另行评估成熟服务能力，不伪称已具备。
5. 服务端配置保存后用隔离邮箱真实测试：正确、错误、过期、重发、新客户端和直接调用认证接口超过阈值。必须绕过界面倒计时测试。实际已验证服务端拒绝无效验证码并触发限流；Supabase 按 IP 使用令牌桶，通常最多允许约 30 次短时突发，配置的 5 次/5 分钟控制补充速率，不是固定窗口第 6 次立即拒绝，也不是单个验证码连续失败锁定。真实签发验证码静置 300 秒后的过期测试、控制台日志交叉核对尚未单独完成。
6. 应用数据根目录设在 **D 盘**（当前安装布局对应 `D:\SOFTWARE\轻笺\data`）。打开“设置 → 账号”，只填写同一个项目 URL 和 Publishable / anon key。新电脑同样配置这两项公开参数。复制 `.example.json` 不是必须步骤；不把管理 Key 填入应用。
7. 登录测试邮箱并重启进入独立账号工作区。首次选择“备份并加入”或“仅使用账号内容”；正式上传需用户单独授权。先用合成内容在两个独立客户端验收，再由用户决定是否关联真实便签。QQ 邮箱验证码必须实际收取并验证。

**最少需要用户提供/完成**：Free 项目的创建授权；选择现有独立发件服务并在云端自行填写 SMTP 凭据；提供项目 URL 与公开 Key；提供本人可收取验证码的 QQ 测试邮箱并完成收信。无需提供收件邮箱密码、管理密钥或笔记正文。没有发件服务和云端配置仍可正常本地使用。

## 本地归属与隔离

- 未登录继续使用原 `qingjian-v1.sqlite3`，不新增同步触发器或上传任务。
- 每个项目、每个账号有独立目录：`<基础数据根>/accounts/<项目URL摘要>/<账号UUID>/data`。SQLite、WebView、备份登记、音频会话记录及设置均随工作区隔离。工作区中的设备设置都是本机设置，不上云；首次进入账号工作区需重新核对设置。
- `cloud-config.json` 只存公开 URL/Key；`active-account.json` 只存账号 UUID、邮箱及项目摘要。刷新令牌仅保存在 Windows 凭据管理器（按基础根目录、项目及账号隔离）；访问令牌只在 Rust 内存，前端、SQLite、localStorage、内容备份和日志均不保存令牌。
- 账号切换使用显式重启，清空 React 草稿、提醒草稿、录音界面与 WebView 缓存。认证请求期间阻断编辑与导航。未保存的正文、提醒或转写草稿、导入/录音任务会阻止切换。
- 退出停止旧账号同步、删除本机会话凭据与选择标记；有内存访问令牌时尝试向服务端撤销该设备会话。离线退出不依赖服务端；未完成的远端撤销依赖服务端原会话有效期，不声称离线已撤销云会话。账号缓存、队列与云端内容保留，再登录同账号继续。B 的缓存与队列不读取 A 的目录。
- 此隔离覆盖应用工作区和服务端权限；本机 SQLite 缓存未新增磁盘加密，同一 Windows 用户仍有文件访问权。共享电脑需要独立 Windows 用户账号才能进一步隔离文件访问。
- Windows 系统凭据服务的内部存储由系统管理；本次不在 C 盘创建源码、测试产物、备份、报告或下载文件。不承诺 Windows 自身的系统文件完全不写 C 盘。

首次关联是**复制**未登录工作区的已保存内容，不移动、不覆盖原库；此后未登录副本与账号副本分别编辑。来源 UUID 保持稳定；关联与标记在同一事务完成，重复点击/重新登录不再次导入。同 ID 已存在则保留账号内内容，原本地内容仍在原库及关联快照中。账号与云端同 ID 并发则通过 CAS 保留冲突副本。

确认前后台不拉取也不上传任何内容；选择“仅使用账号内容”后，只拉取该账号云端记录，原本机内容留在未登录工作区。首次关联或后续账号内新建、导入、恢复的内容均属于当前账号，会进入该账号队列。

## 同步与冲突规则

1. 本地保存仍为 SQLite 事务。触发器与内容一起记录待同步状态，覆盖手动保存、导入、恢复备份、置顶、排序、删除及恢复；仅提醒变更不排队。
2. 每轮先将当前正文、序号、云端基线版本与随机操作 UUID 固化到 SQLite outbox，再发 HTTP。断网/崩溃后重试同一个操作，不重复创建云端记录；发送过程中再次保存，只确认旧序号，新修改继续排队。
3. 云端 `(owner,id)` 唯一。RPC 内从 JWT 读取 `auth.uid()`，客户端不能指定 owner；RLS 限制读取，撤销客户端直接写表权限。写操作使用事务账号锁及 `base_version == cloud_version` 比较，不用设备时间决胜。
4. 版本不一致时，在本机事务内保留当前本机冲突副本，再应用云端版本，原条目本地 revision 递增。冲突副本会作为新 UUID 内容同步；可打开两个版本手工比较合并、保存后标记已处理，不自动删除副本。
5. 后台拉取只刷新列表与没有未保存修改的草稿。未保存草稿保持原内容；保存时本地修订校验拒绝覆盖新版本，界面提供“另存草稿副本”。远端删除也不清空正在编辑的草稿。
6. 回收站软删除及恢复进入版本比较。永久删除保留云端墓碑，清空云端当前正文；旧设备同 ID 无法复活。旧设备有未上传修改时保留新的冲突副本，不丢失其正文。回执只保存摘要与版本。Supabase 内部备份/日志保留遵循平台政策，客户端不承诺物理抹除所有平台副本。
7. 60 秒自动轮询，失败逐步退避至最多 15 分钟，支持“立即同步 / 重试”；每轮最多上传 200 条，云端按 UUID 每页 100 条扫描版本索引，仅下载版本变化的正文。第一版适合个人少量内容，即使正文没有变化，版本索引与请求仍会消耗出站流量，海量内容应改用经过提交顺序证明的增量游标。
8. “已保存到本机”和“已同步”分别展示；只有实际网络操作成功才写最近成功时间。中途失败仍显示失败，本地保存不回滚。未配置时不伪造身份或同步成功。

同步字段：UUID、便签/笔记类型、标题、纯文本正文、`qingjian-rich-v1` JSON 结构、创建/修改时间、软删除/恢复、永久删除墓碑、置顶与列表排序。快捷标签（pins 表）、提醒及完成历史、录音原文件、模型/API 密钥、新闻、窗口与设备设置都不上传。

**提醒仅存在当前电脑当前工作区**。首次复制内容不复制提醒；云端拉取新增内容没有提醒。对原条目应用云端正文仍保留本机已有提醒；云端软删除使本机提醒暂时隐藏，恢复后原本机提醒可再次显示；永久删除按原级联关系删除本机提醒。同步状态“已同步”只表示内容字段，不表示提醒已同步。

## 备份与恢复

关联前：在原本地数据根目录 `backups/首次账号关联前-<UUID>.sqlite3` 创建一致性快照，运行 `PRAGMA integrity_check` 通过后才导入。失败不设置关联完成标记、不上传。快照包含原本地全库（含本机提醒及公开设置），不含 Windows 凭据和录音文件。

日常仍使用原 `.qjbackup` 导出/恢复功能。`.qjbackup` 不包括同步账本、令牌或录音文件，恢复内容时仍采用当前账号同步基线和冲突规则；不能将内容备份当作完整账号环境迁移。

完整账号恢复应先退出所有轻笺进程，备份整个对应账号目录；用 SQLite 一致性快照验证后恢复同一账号的数据库，保留 outbox/meta。不要把 A 的缓存复制成 B，也不要直接网盘同步 SQLite 文件。旧版应用只打开原本地数据根目录，不应指向新账号目录。

需要恢复首次关联前的原库时：完全退出应用，另存当前数据库及 WAL/SHM，验证快照 integrity_check；由维护者用 SQLite backup API 恢复到原本地数据库（或切到单独 D 盘恢复目录），保留原文件可回退。不要运行中覆盖主文件，不自动执行恢复。源码原件备份见交付报告。
